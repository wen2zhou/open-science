# macOS 本地自更新验证

这套开发工具在应用进程外运行：捕获当前工作区的固定源码快照，用同一份快照构建低版本 A 和高版本 B，然后只启动 A。本地更新源提供 B 的 ZIP，用于版本发现、真实下载和校验。默认 `upgrade` 场景由 A 执行任务检查和后台停服，再通过生产安装器真实替换应用并自动启动 B。观察程序核验安装回执、完整应用包、新进程身份及原数据保留；您还需在 B 中完成 Notebook 写入并正常退出。其余故障场景按各自条件验证拦截和恢复。

## 准备并启动 A

运行条件：原生 macOS arm64/x64、Node/npm、Xcode Command Line Tools、可下载固定版本依赖和资源的网络，以及容纳两份依赖目录和应用包的磁盘空间。构建需要数分钟。本地包使用已有的 `build/icon.icns`，不要求安装完整 Xcode 中的 Icon Composer。

请在包含本工具的工作树根目录执行。目前本任务位于独立工作树：

```sh
cd /Users/wen2zhou/Documents/github/fearless82/open-science/.worktree/local-update-validation
npm run validate:update:local -- start --a 0.0.1 --b 0.0.2 --scenario upgrade
```

其他机器请将 `cd` 路径替换为实际工作树路径。如果使用 `HTTP_PROXY` / `HTTPS_PROXY`，可以启用 Node 24 的代理支持，保持下载校验开启：

```sh
NODE_USE_ENV_PROXY=1 npm run validate:update:local -- start --scenario upgrade
```

默认版本为 A `0.0.1`、B `0.0.2`。两者必须使用稳定版本格式 `x.y.z`，B 必须高于 A；A 必须高于 `0.0.0`，以便单独验证低版本场景。

工具会输出运行目录，默认位于 `~/Library/Caches/Open-Science-local-update-validation/<UUID>`。可通过 `--parent /absolute/path` 指定工作区外的其他位置。下文的 `/absolute/run-directory` 均需替换为工具输出的本次运行目录绝对路径。

准备过程包括：

1. 读取 Git 已跟踪文件和未被忽略的新增文件，包含已暂存、未暂存修改及已跟踪文件的删除。捕获前后比较文件清单、内容和符号链接；遇到并发编辑则拒绝继续。Git 暂存区保持不变，捕获后的编辑不会影响本次 A/B。
2. 创建独立构建副本，仅覆盖副本中 `package.json` 和 `package-lock.json` 的版本号。源码快照不包含 Git 元数据、依赖目录、被忽略的文件或旧构建输出。
3. 在每个副本中运行仓库的 `scripts/ci/npm-ci.mjs`，包括 postinstall、Prisma 生成及固定版本的原生组件准备。通过 `fetch-micromamba.mjs` 获取固定版本的 micromamba，通过 `stage:node-runtime` 校验固定版本的 Node 运行时，然后执行 `npm run build:mac`。已有的 `beforePack` 钩子负责构建并打包真实后台。这一步重新构建应用；资源下载缓存仍须通过校验。
4. 在 A 的构建副本中执行普通构建与测试构建的真实主进程包边界测试，保存 `build-boundary-tests.json`。检查桌面端和后台版本一致，记录 ZIP/blockmap 大小及 SHA-256、SHA-512。扫描 A/B 完整 `.app` 目录，包括 ASAR、解包文件和后台资源，确认不含外部测试程序。再复用同一快照已准备的资源，关闭测试标志，构建普通 `.app`，检查其不含测试模块、运行时测试启用入口和外部测试程序。普通包不会启动。测试包使用独立 App ID、回环更新源、显式构建标志和测试安装适配器。
5. 为每个场景创建独立的 HOME、配置、数据、Electron 用户目录、更新缓存和 A 应用包目录。自动准备独立钥匙串，搜索列表仅含该钥匙串，并验证日常 HOME 的默认钥匙串、搜索列表和偏好文件未改变。保留生产凭据辅助逻辑和签名策略。通过生产存储接口离线写入固定数据，在可用的 `127.0.0.1` 端口启动 HTTP 更新源，通过健康检查后再打开 A。

准备失败时保留源码和诊断，不启动应用。快照不会导入 `.env`、真实研究数据或工作区的 `node_modules`。依赖或资源准备失败可查看 `build-a.log`、`build-b.log`；工具不会回退到正式更新源。

## 在 A 中操作

通过 A 的更新界面执行检查、下载、取消、重试、安装和恢复。测试程序不会替您点击这些控件，也不会代替应用停服或恢复。

**由工具启动 A 后，不要再从 Finder 手动打开同一测试应用，以免重复启动。**

固定项目 **Local update validation** 包含历史对话、附件、非敏感设置，以及保存了输出 `LOCAL_UPDATE_SAVED_OUTPUT: 42` 的 Notebook。场景目录中的 `fixture-manifest.json` 提供确切路径及可直接查看的内联命令。会话工作目录、Notebook 工作区、PID 标记和恢复写入均使用生产 Notebook 数据目录 `<dataRoot>/notebooks/<project>/<session>/data`，位于已有沙箱授权范围内：

- `taskCommand`：在应用的 Notebook 命令行中运行，启动本地 shell/sleep 任务，无需模型凭据或 Python。如果 PID 标记无法写入，命令会在启动 sleep 前失败；成功后使用 `exec` 保持记录的 PID。通过应用停止任务，以验证活跃任务阻塞和应用自身的进程清理。
- `postUpdateWriteCommand`：真实升级并自动启动 B 后，在原 Notebook 命令行中执行。报告同时检查持久化的成功执行记录、输出及新文件；单独创建文件不能证明升级后可用。
- `recoveryWriteCommand`：应用恢复后，在同一 Notebook 命令行中运行，在原工作区创建 `recovery-write.txt`。文件时间戳必须晚于恢复事件；恢复前的写入不能证明恢复后仍可写。

默认 `upgrade` 场景：在 A 点击下载及安装，等待安装器自动启动 B；在设置中确认版本为 B，打开固定历史、附件及 Notebook，确认保存的输出仍在，再执行 `postUpdateWriteCommand`。通过应用菜单正常退出 B，最后在终端按 `Ctrl-C` 保存报告。不要手动启动 B，手动启动不能通过自动重启验收。

`boundary` 和安装交接故障场景会截停安装并保留恢复入口；通过该入口使用原有固定数据恢复服务。测试程序不会自行重启后台，也不会重新初始化数据来满足恢复检查。

未发生后台停服的场景，应先通过应用菜单退出 A，再结束观察，让测试程序确认 A 退出后更新源仍然可用。已发生后台停服的场景，可以在 A 界面仍打开时结束观察。在终端按 `Ctrl-C` 只会关闭更新源并保存报告。**请通过应用自身操作退出 A 及其后台。** A 停服或退出不会自动关闭更新源；开始下一个场景前，请正常退出当前 A。

## 复用已经构建的 A/B

“复用构建产物”是指：第一次已经构建好了 A 和 B，验证同一份源码的其他场景时直接使用这两个包，无需重新编译。每次场景仍会创建独立测试数据、A 应用副本和空更新缓存。

如果只想构建，暂不打开应用：

```sh
npm run validate:update:local -- prepare --a 0.0.1 --b 0.0.2
```

使用输出的运行目录执行某个场景：

```sh
npm run validate:update:local -- run /absolute/run-directory --scenario handoff-failure
```

**修改代码后，如需验证新改动，必须重新执行 `start` 或 `prepare`。** 对旧运行目录执行 `run`，验证的仍是旧源码快照。

## 十一个验证场景

这些场景分别覆盖版本判断、下载可靠性、文件完整性、安装前保护及失败恢复。正常下载成功不能替代其他故障场景的验证。

| 场景标识           | 应用内操作及通过条件                                                                                                                                                                                                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `upgrade`          | 在 A 中下载并安装。生产安装器真实替换 A 并自动启动 B；观察程序核验回执、完整安装包及新桌面/后台进程身份。在 B 检查原数据并运行 `postUpdateWriteCommand`，正常退出 B 后结束观察。                                                                                                                    |
| `boundary`         | 发现并下载 B，再触发安装。真实下载校验和后台退出必须先于被截停的安装交接；A 保留恢复入口。                                                                                                                                                                                                          |
| `handoff-failure`  | 下载并触发安装。真实停服后，适配器注入交接失败。通过 A 恢复服务，再运行 `recoveryWriteCommand`；原数据必须保留，恢复后必须能写入新文件。                                                                                                                                                            |
| `same-version`     | 检查宣告 A 当前版本的更新清单。A 必须显示已是最新版本。                                                                                                                                                                                                                                             |
| `lower-version`    | 检查宣告 `0.0.0` 的更新清单。A 必须显示已是最新版本。                                                                                                                                                                                                                                               |
| `download-cancel`  | 首次 ZIP 下载会限速，出现真实进度后取消，再以正常速度重试。必须有部分下载进度、生产状态从 `downloading` 回到 `available`、首次传输在重试请求前被中断，以及重试后的真实下载和校验成功。仅在随后应用退出或更新源关闭时才中断，不算通过。                                                              |
| `network-failure`  | 首次 ZIP GET 请求返回 503。A 显示失败后重试，完成真实下载并通过校验。                                                                                                                                                                                                                               |
| `checksum-failure` | 更新清单声明错误的 SHA-512，文件字节保持不变。下载校验必须拒绝该文件，不能进入待安装状态或安装交接。                                                                                                                                                                                                |
| `corrupt-artifact` | 更新清单中的校验值正确，但更新源修改传输中的一个字节。校验必须拒绝该文件。                                                                                                                                                                                                                          |
| `active-task`      | 下载 B，运行 `taskCommand`。等待终端出现 `Observed local task running` 后尝试安装：Notebook 任务必须阻止安装，后台保持可用。通过 A 停止任务，等待观察到任务退出。重试安装到达交接边界，通过 A 恢复，再运行 `recoveryWriteCommand`。原任务 PID 必须保持退出，`task.pid` 内容不变，任务不得自动重跑。 |
| `shutdown-failure` | A 请求更新清单时，更新源为其运行时锁创建一个真实的自有硬链接。下载并触发安装，停服确认必须失败。打开终端输出的回环诊断页面，释放更新源自有链接，再通过 A 恢复并运行 `recoveryWriteCommand`。必须未进入安装交接、原数据保留且恢复后有新写入。                                                        |

故障在准备场景时选定，不能在场景中途切换。更新源提供版本、网络、校验值和文件损坏故障；测试适配器提供安装交接失败。

在 `shutdown-failure` 中，更新源仅在该场景的 `source-resources/` 下创建额外硬链接，使已有锁文件的链接数增至二。它不改变原文件字节、不替换锁，也不停止进程。生产停服确认会拒绝这个真实的不安全归属状态。诊断页面要求带有本次运行随机令牌的同源 POST；更新源重新检查规范路径、设备和 inode 后，**只删除自己创建的额外链接**。随后仍须通过 A 恢复。更新源退出时也会清理残留的自有链接，但仅有清理不能替代用户释放、应用恢复和恢复后新写入的证据。

## 报告和诊断

```sh
npm run validate:update:local -- report /absolute/run-directory
```

`result.json` 和 `summary.md` 在观察期间更新，结束时保存。内容包括运行标识、Git 提交、源码快照 SHA-256、版本、产物校验值、场景通过/失败/未执行状态、故障实际触发情况、停服与恢复观察、数据保留、新写入、任务 PID 清理、交接边界和诊断路径。

包检查覆盖真实的普通/测试构建产物及三个完整 `.app` 目录。普通包仅为验证打包边界而使用本地 ad-hoc 签名和已有 ICNS；正式签名、公证及分发需要另行验收。

单个场景成功不代表整套验收通过。所有必测场景和打包边界都必须有证据。每个通过的场景还必须证明：A 启动前更新源已就绪，A 停服或退出后更新源继续健康，结束观察后更新源已关闭且 TCP 端口已释放。测试设施故障不能计为成功。只有 `upgrade` 场景允许且必须完成原生安装和 B 自动启动；其他场景发生原生安装调用、B 启动或 `installed` 结果仍会阻止整套验收通过，后续重试不能掩盖这些异常。

```text
source.json                          # 提交、快照标识、文件哈希和符号链接
source/                              # 固定源码快照
builds/{a,b}/                        # 独立依赖和构建副本
artifacts/{a,b}/                     # A/B 应用包、ZIP 和 blockmap
artifacts/production/                # 普通应用包，不会启动
production-package-verification.json # 完整应用包和文件边界证据
build.json, build-{a,b}.log           # 版本、产物、准备信息及日志
scenarios/<scenario>-<UUID>/
  local-update.json, launch.json      # 本地更新源、隔离路径和 A 启动信息
  home/, config/, data/, apps/        # 场景独有资源
  source-resources/                  # 更新源拥有的故障链接
  keychain-verification.json         # 钥匙串隔离及日常 HOME 未变证明
  electron-profile/, update-cache/
  fixture-manifest.json              # 固定数据、任务和恢复写入命令
  fixture-verification.json          # 数据保留和新写入的只读检查
  app-events.jsonl, application.log   # 真实应用状态和诊断
  server-events.jsonl                # 请求、故障触发和更新源生命周期
  observations.jsonl                 # 进程退出、恢复和更新源健康观察
result.json, summary.md
```

对于可恢复的应用故障，测试程序会保留现场，等待用户操作，不会自行代替应用停服或恢复。真实安装、自动启动及升级后数据检查只有在 `upgrade` 场景的完整证据通过后才标为已验证。

## 常见问题

- **凭据初始化导致启动失败：** 本地任务无需模型凭据，但生产原生凭据初始化仍会执行。出现 `CREDENTIAL_IDENTITY: native-secret-operation-failed` 时，保留 `application.log` 和后台日志，再通过 A 退出。启动失败不能算更新交接通过。工具不会切换到明文存储或绕过原生凭据检查。
- **意外出现 `installation-busy`：** 查看安装占用诊断。A 自身的 Crashpad 处理进程属于当前应用，不应被误判为另一个安装使用者；其他运行实例仍是有效阻塞项。
- **停服确认失败：** A 的更新弹窗应保留恢复入口。硬链接故障场景中，先在本地诊断页面释放额外链接，再通过 A 恢复；不要删除原始锁文件或伪造正常退出证据。

## 显式清理

先结束观察，并通过应用自身操作退出所有 A。清理命令只接受带有匹配归属凭据的规范运行目录绝对路径。工具会检查进程命令和打开文件的引用；如果目录仍被使用，或无法证明已不再使用，就会保留目录并说明原因。工具不会终止应用或后台进程。

```sh
npm run validate:update:local -- clean /absolute/run-directory
```

失败证据会一直保留，直到显式清理；没有自动过期删除，也不会影响日常安装或真实配置。

自动化测试覆盖源码快照和暂存区保护、真实回环传输及故障、端口归属和释放、证据顺序、配置隔离，以及真实停服证明失败时拒绝交接。它们不能替代在打包后的 A 中执行全部十一个场景。

## 代码变更后的使用和维护

普通页面或业务功能改动通常不需要修改验证工具，但验证新代码必须重新构建 A/B。以下变更需要检查工具是否仍与应用行为一致：

- 更新器或 Electron 升级：检查下载、取消及安装交接接口。
- 后台进程、任务或恢复机制调整：同步观察方式和通过条件。
- 数据结构或 Notebook 接口变化：调整固定测试数据和操作步骤。
- 打包方式变化：更新构建流程及正式包隔离检查。

当前 `patches/builder-util-runtime+9.7.0.patch` 修复完整下载路径取消后未中断 HTTP 请求的问题。依赖升级时应检查上游是否已修复；若已修复，移除补丁并保留下载取消回归测试。本地 macOS 场景不能证明其他平台或差分下载路径已经通过验收。

日常小改动可先运行相关自动化测试。涉及更新、进程生命周期、存储或打包的改动，以及发布前，建议执行完整场景验收。本地真实安装使用 ad-hoc 签名及直接启动包内可执行文件，以保留隔离环境。正式发布还需验证正式签名、公证、Gatekeeper、LaunchServices 启动和生产更新源；本地结果不代表历史版本数据库迁移已经通过。
